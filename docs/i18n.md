# Internationalization (i18n)

next-intl v4 · locales: `vi` (mặc định), `en` · prefix: `always` → `/vi/...`, `/en/...`

## Thêm string dịch

Mọi string hiển thị phải qua next-intl — **không hardcode**.

```ts
// Server Component
const t = await getTranslations("mySection")
// Client Component
const t = useTranslations("mySection")
```

Thêm key vào **cả hai** file trước khi dùng:

```json
// messages/vi.json
{
  "MyFeature": {
    "title": "Tiêu đề",
    "actions": {
      "create": "Tạo mới",
      "delete": "Xóa"
    }
  }
}

// messages/en.json — cùng structure, khác value
{
  "MyFeature": {
    "title": "Title",
    "actions": {
      "create": "Create",
      "delete": "Delete"
    }
  }
}
```

> Thiếu key ở một ngôn ngữ → next-intl throw lỗi. Luôn thêm cả hai file cùng lúc.

## Thêm locale mới

> **Hỏi trước khi làm** — ảnh hưởng đến routing và proxy.

1. Thêm locale vào `src/i18n/config.ts`
2. Tạo file `messages/[locale].json`
3. Kiểm tra `PUBLIC_PATHS` trong `src/proxy.ts` có cần update không
4. next-intl tự xử lý routing qua `defineRouting()`

## Cách locale được resolve

App không dùng middleware gốc của next-intl (đã có `src/proxy.ts` riêng cho auth), nên `src/proxy.ts` tự forward header `X-NEXT-INTL-LOCALE` (tính từ URL) trên mọi request — đây là cơ chế next-intl dùng để resolve locale cho `getTranslations()`/`getLocale()`/`getMessages()`. Thiếu header này, next-intl luôn fallback về `defaultLocale` bất kể URL là `/en` hay `/vi`.

Vì locale được đọc từ header ở **root layout** (`src/app/layout.tsx`, nằm ngoài segment `[locale]`) chứ không phải route param, `router.push()` khi đổi ngôn ngữ không tự invalidate Client Cache của root layout — `src/components/layout/language-switcher.tsx` phải gọi thêm `router.refresh()` ngay sau `router.push()` để root layout đọc lại header mới. Nếu sau này thêm chỗ nào khác cũng chuyển route kèm đổi locale, nhớ áp dụng lại pattern `push()` + `refresh()` này.
